01 / Introduction

How to trust a computer

Not “is it safe?” but what can it prove?

An eight-minute tour of the machines in my home lab, and the kind of question I work on as an Infrastructure Security Engineer.

Speaker notes · 0:40

My job title is Infrastructure Security Engineer at ElevenLabs. That sounds abstract, so here is a concrete question I keep coming back to: if a computer asks for access, how do we know it's the right one, running what we expected? My home lab is where I build and test my own version of this idea. It is not a diagram of ElevenLabs systems.

02 / The problem

A name is not evidence.

Any computer can say “I’m the server.” The network hears the same sentence from the real one and an impostor.

This is why a hostname, a login screen, or a serial number on its own cannot establish trust.

Speaker notes · 0:50

This is the actual problem: computers are excellent at saying things about themselves. A name is useful for finding a machine, but it isn't proof that we are talking to the machine we meant to find. At home, I have a list of machines I intend to run. A machine showing up with the right name doesn't automatically get a place on that list.

03 / Identity

A key the computer cannot hand over.

The TPM is a small hardware vault. Instead of revealing its private key, it uses the key to answer a fresh challenge.

A TPM proves possession of a key. A human still has to decide which keys belong to invited machines.

Speaker notes · 1:05

TPM means Trusted Platform Module. It can protect a private key so the computer doesn't have to hand the key to anyone. We send a new random question; the chip signs an answer, and we check it. A recording of yesterday's answer won't work because today's question is different. This establishes that we're talking to hardware holding the expected key, but someone still has to decide which machine is supposed to be here. In my lab that's tied to the inventory and, where available, proof from the hardware manufacturer.

Lab example: how fleetd checks a machine

04 / Boot state

Who are you is only half the question.

The computer may be the right one but start with the wrong software. Its boot leaves a record we can check.

Speaker notes · 1:05

There are two ideas people often mix up. Secure Boot checks signatures when software starts. Attestation later asks the chip for a signed report of the boot measurements, and a verifier compares the boot log and measurements against an allowed recipe. That gives useful evidence of how the machine started. It does not prove there are no bugs, or tell us everything it does after boot. Keeping that limit in view matters.

Lab example: boot policy and node lifecycle

05 / Admission

Proof comes before a job.

In my lab, a new machine doesn’t get installation instructions just because it appeared on the network.

A passing check earns a narrow next step. It isn’t a lifetime certificate of goodness.

Speaker notes · 0:55

Here is what this looks like in my own lab. I declare a machine in an inventory. When it boots, it sends hardware and boot evidence to a service called fleetd. The service checks that evidence against what we expected. Only after a pass does it give the machine the code it needs to install itself and join the group. If it cannot prove its identity, it waits rather than getting installation instructions. This is a practical example, not an ElevenLabs architecture diagram.

Lab example: the admission sequence

06 / Permission

Admitted does not mean all-access.

A trusted machine runs many programs. Each program needs its own identity and only the permission its job requires.

Short-lived credentials make it possible to keep asking “do you still belong here?”

Speaker notes · 1:00

Even a correctly admitted computer shouldn't be a master key. My lab gives identities to individual workloads — the little programs that run on that machine. A backup program can use its identity to request access to backup storage; a website on the same computer shouldn't get that permission. The credentials expire and can be renewed when the machine and workload are still eligible. The rule deciding access is separate from proving identity.

Lab example: node and workload identity

07 / Time

Trust has to be checked again.

A machine that passed on Monday might fail on Tuesday. The response has stages, not a magic off-switch.

In the lab, an authenticated boot-policy failure quarantines a worker; a control-plane failure alerts without an automatic cordon.

Speaker notes · 1:05

My lab periodically checks its running machines. If a worker produces authenticated evidence that fails the boot policy, it gets quarantined and its credentials stop renewing. That doesn't mean every credential it already has vanishes immediately. Some may remain usable until their expiry, so the expiry time and separate access controls matter. For machines that keep the cluster itself running, the lab reports and alerts instead of automatically cordoning them. That tradeoff is part of security engineering too.

08 / My work

Make the decision repeatable.

My work is helping teams build infrastructure where access follows evidence and policy, not a hopeful assumption.

The examples here are from my personal lab. They describe the problem I care about, not ElevenLabs’ internal design.

Speaker notes · 0:55

In a family-sized sentence, this is my job: make it easier to answer these questions consistently for the systems people rely on. Decide who belongs, collect evidence, give only the access needed, and revisit the decision. Engineering this well means it has to work on a normal Tuesday, not just in a diagram. The lab is my own playground for these ideas; I'm not presenting internal details about ElevenLabs.

09 / Takeaway

Trust is a decision with an expiry date.

Who is it?
How did it start?
What may it do?
When do we check again?

That’s the work. Questions?

Speaker notes · 0:30

If you take one thing away: trust isn't a property that a computer simply has. It is a decision we make using evidence, for a particular job, for a limited time. I promise the next time I say I'm working on “attestation,” you can just ask me which computer I'm asking to prove itself.
