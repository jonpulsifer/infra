Bosun

A skiff is already booted before the job exists. It serves exactly one, and then it is scuttled.

Nothing dispatches it. That one inversion is why there is no webhook, no queue, no inbound port and no control plane to run.

02 / 11

The problem

“I pushed. Now everybody waits.”

Before a job computes anything it re-acquires a machine, a toolchain and a cache it already had the last time it ran. That tax is fixed, it is paid again on every push, and a bigger runner does not remove it — a faster CPU runs the same six steps.

None of this is your build. All of it is on the critical path between a push and an answer.

  1. Wait for a runner — a pod, a VM, a slot
  2. Pull the toolchain image
  3. Restore the dependency cache over the internet
  4. Install a toolchain the last job also installed
  5. Run the build you actually wanted
  6. Share a kernel with whatever ran before you

measured on one real repository's suite — restoring a dependency cache over the internet 49–76 s · waiting for a container runner 1–59 s · the same cold suite on a hosted runner 271–375 s, same commit, different days

The lever everyone knows about is to run it somewhere else. Almost nobody pulls it, because CI is welded to the place the code lives: the label, the cache, the queue, the identity and the logs all belong to one vendor, and moving the compute has meant giving up all five.

03 / 11

The whole idea

Nobody dispatches a skiff. It is already there.

Warm pool, not dispatch.

What that deletes

No webhook endpoint. No inbound connectivity. No queue API. Nothing to replay after a restart, because there is no delivery that could have been missed.

What it costs, said out loud

Idle skiffs hold RAM, and there is no scale-to-zero. A pool is a standing reservation — which is exactly why a class is a declared number and not an autoscaler.

04 / 11

What adoption costs

One line moves, and it is the label

-  runs-on: ubuntu-latest
+  runs-on: skiff-ubuntu

The workflow is otherwise untouched. Same steps, same third-party actions, same actions/cache — the stock action, which the hull points at a cache service on the host's own disk instead of one across the internet.

Nothing about a skiff is visible to the job running inside it. A runner you have to write YAML for is a migration, not a runner.

1line changed in the workflow
0firewall changes — a pool only ever dials out
14 scache restore on-host, against 49–76 s over the internet
1 squeue to start, on every run

Two shapes already exist for this. One keeps your workflow and swaps the hardware behind the label. The other keeps a hosted orchestrator and moves the agents onto machines you own. This keeps the label, moves the machines, and then deletes the orchestrator — because a warm pool never needed one.

05 / 11

Four nouns, and the seam between them

The hull describes itself. bosun never learns why.

skiffone microVM · one job · then scuttled
hullthe kernel + initrd it boots from
classwhat a runs-on: label resolves to
bosunthe daemon, and the project

A hull is a directory holding a hull.json beside the files it names — a kernel, an initrd, a command line, and a list of devices. bosun translates that manifest into hypervisor arguments and provisions what it asks for.

There is no per-family branching anywhere in the daemon. Two unrelated operating systems boot through one code path.

bosun promises every skiff

  • A credential, at a contract-fixed location
  • A workspace, at a contract-fixed location
  • Outbound network
  • Its own identity on the kernel command line — declared to be a correlation fact, never a claim

A hull promises

  • Boot from what it declared
  • Find its credential
  • Run one job
  • Halt — and this clause is enforced by GitHub, not by anyone here, because a JIT runner deregisters itself

the contract names no runner, no version, no operating system and no package manager

Two hull families exist today: a NixOS hull that mounts the host's own /nix/store read-only, and an Ubuntu hull that is an ordinary container image flattened into a read-only squashfs. The daemon cannot tell them apart — which is why the shared store is a property of one hull and never of the platform. One implementation would have made this seam hypothetical; two is what makes it real.

06 / 11

The standing rule

If an answer adds a component, it must say what it deletes

2,287lines of Go, in eight files
0third-party dependencies
0inbound ports on the daemon
0databases

State lives in /run/bosun/<id>/, which is tmpfs — so a reboot clears it, and that is correct. Desired state is one config file on the host, which is why the daemon has no runtime configuration surface at all: no API that can resize the pool, and so no drift between what is running and what was declared.

  • The webhook receiver — a warm pool is never told a job was queued, so there is nothing to receive.
  • The queue listener and the control plane — both existed to answer a question the inversion deleted.
  • Credential transport over vsock — a kernel module, a CID allocator and a guest listener, for one string delivered once at boot. It is a file in a per-skiff directory instead.
  • Snapshot and restore — measured, not assumed: restore is flat at ~1.8 s, and the Ubuntu hull reaches the runner in 0.68–0.97 s. A snapshot cannot pay for itself against a guest that cheap.
  • Re-adopting an orphaned hypervisor — systemd SIGKILLs the whole cgroup at the stop timeout, so a VMM cannot outlive the daemon and be found again later. Sweeping stale registrations on start is the entire recovery path.
07 / 11

Isolation is the floor, not the feature

Deny the LAN. Allow the internet.

The obvious policy — “reach the CI provider and nothing else” — breaks every real job, which pulls package registries, base images and release binaries from a dozen public hosts. So invert it. One IPAddressDeny on bosun's own unit denies RFC1918 and 169.254.0.0/16, and systemd's IP filtering inherits down the cgroup subtree to every skiff underneath it. There is no per-skiff rule anywhere.

A job reaches the internet and cannot reach anything of yours — including the cloud metadata service, which sits on the wrong side of that same line.

The data path

Nothing in it needs root

passt runs unprivileged, virtiofsd runs unprivileged, and /dev/kvm is world-writable. What stays privileged is bosun's own systemd unit — a system user in the kvm group with DevicePolicy=closed.

The credential

Removed the moment it is spent

bosun deletes it host-side as soon as GitHub reports the runner online. virtiofs passes through to the host filesystem, so it vanishes inside the guest with no cooperation from the guest — untrusted job code never sees a live credential.

The tenancy

One job, one kernel

Not a scrubbed workspace, and not a fresh container on a kernel the last job also used. A skiff is its own kernel, and it stops existing when the job ends — so there is no residue for the next job to inherit and nothing to scrub correctly.

Denying RFC1918 also breaks DNS, so a public resolver is pinned and the deny stays absolute rather than growing its first exception. An allowlist with one hole in it is an allowlist nobody can reason about a year later.

The headline is the variance, not the win

Across every table in the record the skiff's spread is a few seconds. Hosted swings 23–49 s on the same cold image build and 271–375 s on the same cold suite. A skiff is the same machine every time.

The gap that closed was a transfer, not a CPU

The original 99 s deficit was 70 s of actions/cache pulling a dependency store over the internet. The answer was not a faster transfer: a class can persist its workspace disk, so the next skiff finds the store already there.

09 / 11

Evidence, not assertion

Five things no test suite was ever going to find

  • The helpers leaked, and a human found it by hearing a fan. Nine hours of two warm classes cost 1d 6h of CPU. passt daemonizes and setsids, so the handle bosun held was an already-exited parent — the real process outlived its skiff and spun at 100% waiting for a second client a one-job skiff never sends.
  • One failed poll killed a healthy skiff. A transient connection reset, one offline observation a minute later, and the guest was destroyed. It was idle; a busy one would have lost its job. Wedge detection now needs three consecutive observations.
  • systemd deletes RuntimeDirectory= on stop — which is exactly the state the start-up sweep reads, so every restart leaked a ghost registration until the directory was told to survive.
  • GitHub silently removes an expired registration while the agent keeps running. A skiff aged past its credential was offered a job at its own label and never claimed it; by 89 minutes the runner was a 404 while the VMM was alive and idle. Without recycling, that is a permanent RAM leak wearing the costume of a healthy skiff.
  • The suite outgrew its class — restored tests that each stand up a database segfaulted at 3 GiB and passed on hosted from the same commit. Long test durations plus a moving crash site is starvation, not a logic bug.

Every one of these was live behaviour on a real host, and none of them is exotic. The generalisable lesson: a code comment reading “if this becomes a problem in practice” is a prediction with no alarm attached to it. That one came true in nine hours.

10 / 11

Beyond CI

A producer that cannot reach the pool can still feed it

No inbound port is the point of the design, and also the obvious objection: how does anything other than GitHub hand a pool work? By not pushing. A producer writes an intent to a row in its own database, and the pool long-polls in to claim it. Spindrift — a deploy control plane, and a peer project, not an owner — routes container builds this way.

Proven end to end

Claim, boot a build skiff, fetch and verify the staged bundle, build, push, report. Spindrift then verified SLSA L2 against the hull's own builder identity and signed the digest — the same signature Kyverno and Binary Authorization each re-check at admission.

Declared, and honestly unserved

The host that served this class is powered down again; answering the benchmark two slides back is what it was woken for. The route stays declared and ranked last, so bringing a host back serves it with no configuration change at all — which is the same claim, tested by its absence.

Where it stands

Two hosts, three warm slots, and an honest open list

Two hostsone on-site, one remote — nothing in common
Three warm slotssame daemon · same hulls · nothing between them

A host joins by importing the module and naming its classes. Nothing coordinates the two, because there is no fleet controller to coordinate with — a pool is per-host by construction, and the only shared fact is a label GitHub already knows how to route on.

Bosun drains on stop rather than dying: idle skiffs are scuttled registration-first — GitHub refuses to delete a busy runner, so a successful delete proves no job can land there — and busy ones get fifteen minutes to finish.

Open

  • The production suite is back on hosted while a class grows — the pool's host shares its box with other workloads, so the class's memory bound is an operator's arithmetic and not a workflow's to make.
  • Every decision that reads GitHub — busy or idle, lifetime, pool count — has the same single-source dependency, and none of them has been thought about under a GitHub outage.
  • What a guest breakout would actually cost, given the data path is three unprivileged processes rather than root.
  • arm64. Native arm64 hosts are sitting right there and nobody has asked the question.
