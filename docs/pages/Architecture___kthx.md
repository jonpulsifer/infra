- kthx is quick static sites: a visitor picks a name, drops an `index.html` or a zip on `https://kthx.dev`, and the site answers at `https://<name>.kthx.dev` from the offsite [[Architecture/Spindrift]] installation. Rollbacks, the hold latch, the archive pipeline, and the source depot are Spindrift's; kthx adds a name and a bearer on top. The reference for what the page says and looks like is the page itself, `packages/kthx/landing.html`.
- ## Where it lives
	- `packages/kthx/` is the half with no runtime behind it: `underscore.ts` is the per-site `/_/` contract over a `KthxStore`, `sdk.js` is what a site loads as `window.kthx`, `landing.html` is the apex page, and `favicon.ts` is the dot a site with no icon of its own answers with. Both hosts import it by name.
	- `apps/spindrift/src/kthx/` is the server side, inside the Spindrift web process: `serve.ts` dispatches on `Host` ahead of every path route and serves a site's files, `sites.ts` is the claim/release/serve/hold API, and `data.ts` is the Postgres `KthxStore` behind the contract. `apps/spindrift/README.md` carries the operator's view; the tests are `apps/spindrift/test/kthx/`.
	- `apps/kthx/` is the CLI: `kthx deploy` mints a name when the directory has none and uploads on the user's behalf, `kthx dev` serves a directory on `:4321` with a local `/_/` that keeps every key, cookie, and room in-process, `kthx rollback` and `kthx release` drive the hold latch. The name sits in `<dir>/kthx.json`; the bearer sits in `$XDG_CONFIG_HOME/kthx/sites.json`, never in the directory. Its `dev` runs `packages/kthx` itself over a `Map` and serves the same `sdk.js` bytes the control plane does, so a site that works locally works deployed.
	- There is no image, chart, pod, or port of kthx's own. The zone the process answers for is `KTHX_ZONE` (default `kthx.dev`), read in `apps/spindrift/src/kthx/serve.ts`.
- ## How a name resolves
	- `terraform/network/cloudflare/kthx.dev.tf` adopts the zone into the account, and `terraform/network/cloudflare/spindrift.tf` routes `*.kthx.dev` through the `spindrift-control` tunnel to the plain-HTTP listener of the `spindrift-apps` Gateway on offsite. Cloudflare terminates TLS; there is no cert-manager wildcard, no external-dns record, and no Gateway listener for the zone.
	- On the Gateway, the `spindrift-status` HTTPRoute in `clusters/offsite/apps/spindrift/status-route.yaml` backs a whole zone onto the control-plane Service, which then tells a kthx `Host` from its own UI and from an App name. Spindrift's status page is what a wildcard over the App zone falls through to; kthx is what a wildcard over `kthx.dev` falls through to.
	- **Divergence, in present tense:** that HTTPRoute carries only `*.${SPINDRIFT_DOMAIN}` today, and the tunnel has no apex rule for `kthx.dev` — `*.<zone>` never matches the zone itself, so the apex needs its own ingress rule the way `clankerbanker.ca` has one. Until both hostnames are added there, a request for `<name>.kthx.dev` reaches the Gateway and finds no route. The control plane's side needs nothing: `withKthxHost` answers any Host under the zone the moment one arrives.
- ## Where bytes live
	- An upload takes the same path as an App's archive source: `normalizeArchive` in `apps/spindrift/src/storage/archive-format.ts` decides zip or tar.gz by magic number and converts a zip to a gzipped tar, `stageArchiveBytes` in `apps/spindrift/src/storage/archives.ts` puts it in the installation's source depot — the GCS bucket the manifest names, durable across pod restarts and image rolls — and the digest names the converted bytes. A release is stored, never rebuilt; rolling back re-reads an older digest from the depot.
	- Serving reads a release back through the same `readBundle` the static deploy backends use and keeps the unpacked files in a per-replica memory cache, refilled from the depot on a miss. A bundle wrapped in one top-level directory is unwrapped; `index.html` must exist at the root after that; `_/` inside a bundle is never served because `/_/` belongs to kthx on every site.
	- The ceilings — compressed size, unpacked size, file count, key and value size, list length — are the named constants in `apps/spindrift/src/kthx/sites.ts` and `packages/kthx/underscore.ts`, not a number here.
- ## The tables
	- A site is **not an App**. `apps/spindrift/src/db/migrations/0057_kthx.sql` declares `kthx_sites` — the name, the SHA-256 of the bearer that owns it, which release number it serves, the `held` latch, and a `deleted_at` that keeps a deleted name answering `410` rather than becoming somebody else's — and `kthx_releases`, one row per upload keyed `(site, n)` with the digest and depot location. `apps/spindrift/src/db/migrations/0058_kthx_kv.sql` adds `kthx_kv`, one JSON value per `(site, key)` with an etag over the canonical JSON that a `PUT` with `if-match` compares-and-swaps on.
	- No Build, no Deploy, no Vessel admission, no Target: the whole product is "which bytes answer for this name", and that is one integer on the site row. Graduating a site into an App is a design question the tree does not yet answer, and nothing in the schema forecloses it.
- ## The public shape
	- The apex speaks `/kthx/*`: claim a name, read a site, upload a release, point `serving` at a release (which sets `held`), release the hold, delete. Claiming is anonymous and returns the bearer once; everything after is `Authorization: Bearer`. Errors are `{ code, message }`. The handlers in `apps/spindrift/src/kthx/sites.ts` are the contract, and `apps/kthx/cli/main.ts` is the reference client. Names match the pattern and reserved set exported beside them.
	- Every site answers under `/_/`: `db` is JSON by key, writable by anyone on the site's origin and compared-and-swapped through `if-match`; `me` is the anonymous `kthx_me` cookie; `ws` is the one socket a tab opens for `db.watch` and rooms; `sdk.js` is the SDK. `window.kthx` fronts the three as `kthx.db`, `kthx.live`, and `kthx.me` — the JSDoc in `packages/kthx/sdk.js` is the surface.
	- Write rules are `anyone` on the site origin, artifacts-style. There is no per-site file store and no owner-only key. Because nobody signs in to write, two ceilings stand between a visitor and the control plane's disk: a site holds at most `MAX_KEYS` keys — checked only where a write would add a row, so overwriting and deleting keep working at it — and writes under `/_/` are held by the same per-address bucket the claim path uses, which reads, `me`, and the `ws` upgrade are not spent against. The constants are in `packages/kthx/underscore.ts`, not a number here.
- ## Honest divergences
	- **One web replica.** Presence is a `Map` in the process and fan-out is Bun's in-process pub/sub, so a `db.watch` or a room only sees writes that land on the same pod. The upgrade path named in `packages/kthx/underscore.ts` is Postgres `LISTEN/NOTIFY` between replicas; until then the chart default in `packages/charts/spindrift/values.yaml` is one web replica, the offsite HelmRelease does not raise it, and the rate limiter and file cache are per-replica for the same reason.
	- **Sites are not Apps.** The Kubernetes deploy adapter is `image`-only and a `files` artifact reaches only the edge Targets, so an App per site would buy nothing served from the lab and cost an adapter kind, a manifest Target, and a vessel. Two tables reuse the archive pipeline, the depot, the process, and the zone instead.
	- **The edge is partly declared.** See the divergence under How a name resolves.
