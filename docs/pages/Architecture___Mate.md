- mate is the Discord bot Rowbutt connects through: a human mentions Rowbutt in an allowed channel of the homelab guild, a public thread opens from that message, and the reply streams back into it, edited in place. Discord's thread is the session; one thread owns at most one sandbox. mate never runs a model itself — it is a gateway client plus an Agent Client Protocol client, and the coding agent it will talk to runs inside a per-thread sandbox on [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox).
- ## Where it lives
	- `apps/mate/src/` is the process: one Bun program with the gateway, the thread contract, the identify-budget guard and `/healthz`. The sandbox side lives there too — the Kubernetes client on Bun's own `fetch` and `WebSocket`, the ACP client, and the `Sandboxes` implementation that mints one Sandbox per thread. `bun test` covers both against fakes, the cluster half against an in-process apiserver.
	- `clusters/offsite/apps/mate/` is the workload on the offsite cluster: the `mate` namespace at Pod Security `restricted`, the ServiceAccount and Role that mint Sandboxes, the ExternalSecrets that carry Rowbutt's token and the OpenCode key from 1Password, an egress policy for the bot and a second one for the sandboxes, and one Deployment. It is raw manifests under Flux, not a chart and not a Spindrift App.
	- `images/mate-sandbox/` is the harness image a sandbox runs: debian-slim with `opencode`, git and ripgrep, uid 1337, and a keepalive PID 1 that mate execs into.
	- `.github/containers.json` names both images in `build` and this Deployment in `deploy`, so every build of `apps/mate` or `images/mate-sandbox` that lands on `main` opens a digest-bump PR through the CD App identity. Both refs in the Deployment carry a digest, which is what keeps the two rewrites off each other: the anchored rewrite matches `ghcr.io/…/mate…@sha256:` and `ghcr.io/…/mate-sandbox…@sha256:` separately, and the unanchored fallback only reaches a manifest that names an image without a digest beside it.
- ## What is true today
	- Every thread gets a real sandbox: `MATE_SANDBOXES` is `kube`, so mate mints one `Sandbox` per thread, execs `opencode acp` in its pod and streams the turn back into the thread. The other value is `stub`, an in-process reply with no cluster behind it.
	- A thread's harness state lives on the sandbox's own filesystem, keyed by the ACP session id mate keeps in an annotation on the Sandbox. mate re-opens it with `session/load`; when that fails — a fresh sandbox after quiet, a harness that cannot replay — the new session's first prompt carries the thread's own transcript, read back from Discord, capped at the newest 40 messages or 8000 characters. mate's own status and teardown lines are not part of it.
	- A turn in flight is stamped on the Sandbox and cleared when the turn ends, so a mate that dies under a running turn knows which threads lost an answer. On the next start it rehydrates from the Sandboxes it finds and tells each of those threads once, in plain words, before carrying on.
	- Every state change of every thread is one info line naming the thread, the state, the sandbox and the turn count. The metrics — sandboxes live, turns started and ended by stop reason, teardowns by reason, time to first token, queue depth, USD per turn — are minted on first use, because an OpenTelemetry instrument created before an SDK starts is a no-op forever. No SDK is registered, so they are inert: the cluster's OTLP collector is in the `monitoring` namespace and mate's egress policy does not reach it.
	- A sandbox reaches three things. Its own `CiliumNetworkPolicy` selects `app.kubernetes.io/name: mate-sandbox` and allows `opencode.ai` and `models.opencode.ai` for the model and `github.com` for the clone, on 443 by name; cluster DNS through Cilium's DNS proxy; and every pod in every namespace on every port — so a job can reach kthx, Spindrift's MCP or a CNPG Postgres, and so it can also read anything else the cluster serves unauthenticated, VictoriaLogs and Prometheus included. Trading that away is one field: an `In` set of namespaces in place of `Exists`. DNS is unrestricted in the same spirit — `toFQDNs` needs the lookups to pass through the proxy, and CoreDNS forwards whatever it is asked. The LAN, the node addresses, anything on host network, the API server and the cloud metadata address are denied by omission, and kata-clh isolates the kernel rather than the network, so this policy is the whole network boundary. In-cluster destinations are named by identity rather than by address because Cilium translates a ClusterIP to its backend before the egress verdict and CIDR selectors do not match in-cluster endpoints: no CIDR appears in the file at all. No ingress rule — exec arrives through the API server.
	- The bot pod holds a ServiceAccount token, so it also holds a `CiliumNetworkPolicy`: egress to Discord by name, to cluster DNS, and to the API server, and nothing else. Cilium enforces per direction, so ingress stays unenforced and the readiness probe keeps working.
	- One replica with `strategy: Recreate`. Discord delivers every event to every gateway session on a token, so two mate pods overlapping on a roll would both reply.
	- The probe is readiness only. `/healthz` answers 503 whenever the gateway is disconnected, including during the budget guard's deliberate sleeps, and a liveness probe on it would kill the process for protecting the identify budget.
	- Gateway session info sits on an emptyDir so a container restart in the same pod resumes rather than identifying again.
	- A rotated token reaches the pod without waiting for Discord to close the stale session: the ExternalSecret refreshes hourly and reloader rolls the Deployment when the Secret changes.
	- No HTTP surface: no Gateway, HTTPRoute, certificate or DNS name. The Discord gateway is an outbound WebSocket.
