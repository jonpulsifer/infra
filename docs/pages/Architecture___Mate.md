- mate is the bot Rowbutt connects through, in two places: a human mentions Rowbutt in an allowed channel, a thread opens from that message, and the reply streams back into it. The thread is the session; one thread owns at most one sandbox, one allowlisted human drives it, and a second human in a thread shares its sandbox. mate never runs a model itself — it is a client of whatever surface it is answering on plus an Agent Client Protocol client, and the coding agent runs inside a per-thread sandbox on [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox).
- ## Where it lives
	- `apps/mate/src/` is the process: one Bun program with the surfaces, the thread contract, the identify-budget guard and `/healthz`. The sandbox side lives there too — the Kubernetes client on Bun's own `fetch` and `WebSocket`, the ACP client, and the `Sandboxes` implementation that mints one Sandbox per thread. `bun test` covers both against fakes, the cluster half against an in-process apiserver.
	- `clusters/offsite/apps/mate/` is the workload on the offsite cluster: the `mate` namespace at Pod Security `restricted`, the ServiceAccount and Role that mint Sandboxes, the ExternalSecrets that carry Rowbutt's tokens, the OpenCode key and the sandbox's own 1Password Connect token out of 1Password, an egress policy for the bot and a second one for the sandboxes, and one Deployment. It is raw manifests under Flux, not a chart and not a Spindrift App.
	- `images/mate-sandbox/` is the harness image a sandbox runs: debian-slim with `opencode`, git and ripgrep, uid 1337, and a keepalive PID 1 that mate execs into. On top of that it carries the toolset this repo's own tasks reach for, pinned version by version in `images/mate-sandbox/Dockerfile` — an agent asked to change infrastructure here has to render manifests, validate OpenTofu, decrypt a sops file and open a pull request, and it can install none of those for itself behind an allow-list four names wide, so what the image does not carry it cannot do. `op` and `gh` are in it because reading a credential and opening a pull request are both how a turn here ends. `nix` is not, and AGENTS.md routes `nixos-rebuild`, the host builds and `nix flake check` through `nix develop`, so those are the tasks an agent in a sandbox cannot run — the same absence is why the checkout's own MCP server, whose command is `nix`, would not start even if its config were honoured. mise itself is in the image for `mise tasks ls`, which is where AGENTS.md sends an agent first: its config in `images/mate-sandbox/mise.toml` trusts `/workspace` so the checkout's task list loads at all in a sandbox that remembers nothing, and manages no tools, because every binary a task reaches for is already a plain file in `/usr/local/bin`.
	- `.github/containers.json` names both images in `build` and this Deployment in `deploy`, so every build of `apps/mate` or `images/mate-sandbox` that lands on `main` opens a digest-bump PR through the CD App identity. Both refs in the Deployment carry a digest, which is what keeps the two rewrites off each other: the anchored rewrite matches `ghcr.io/…/mate…@sha256:` and `ghcr.io/…/mate-sandbox…@sha256:` separately, and the unanchored fallback only reaches a manifest that names an image without a digest beside it.
- ## The surfaces
	- A surface is one place mate is present: its own bot identity, its own allowlists, its own ids. The thread state machine and the renderer only ever see that port, so the caps belong to mate rather than to either place — one queue, one concurrency limit, one daily budget across both, because it is one process. A thread is keyed by its surface, and a Sandbox is named and labelled from that key, so the two estates cannot collide.
	- A thread is answered before it has an answer. A mention waits out a mint, which is tens of seconds, so mate posts one line into the thread saying what it is doing — asking for a sandbox, booting one and cloning the repo, taking a warm one, bringing its checkout up to date, waking the agent — and rewrites that same line as the step and the elapsed count change. It is a message on both surfaces because a thread has nowhere else to put words: the typing indicator and the agent session each say that mate is working and neither can say what it is working on, and a Slack stream chunk would be counted as part of the answer and read back to a fresh harness as something mate said. On Slack it is also the first thing that happens in the thread at all, a mention there having nothing to create. The turn's own frames take it out of the thread; every other ending rewrites it in place instead — the queue a thread joins when every slot is busy, the reason a mint or an attach failed, a budget refusal, and mate being asked to shut down under it. A kill that skips that is what leaves one standing, which is why the line says what mate is doing rather than promising an answer.
	- **Discord.** A mention in an allowed channel of the homelab guild opens a public thread. One reply message is edited in place as text arrives and sealed into a new one at the 2000-character cap, with an italic status line above the live text and a red Stop button below it, both gone when the turn ends. mate archives the thread at teardown, because it is the thread's creator.
	- **Slack.** A mention in an allowed channel of the Folly Mountain Laboratories workspace makes that message the parent of a thread, which is all a Slack thread is. The answer is streamed rather than rewritten: `chat.startStream` and its `append`/`stop` take chunks, addressed to the human who asked with `thread_ts`, `recipient_user_id` and `recipient_team_id`, all three of which a mention already settles. Every stream opens in chunk mode, because the mode is fixed at the first call and a stream opened on plain markdown refuses chunks thereafter. A `markdown_text` chunk is answer text; a `task_update` chunk is one tool call, which Slack merges by its id into a task card in the same message and mutates in place as the call runs, finishes or fails. `task_display_mode` on the first call is the choice of how those same chunks render — a card per call, or the one plan block summarising them — and mate sends `timeline` for the cards, because a turn's tool calls are discovered one at a time rather than announced up front. A card still running when the turn ends is closed with it, complete on a turn that finished and errored on one stopped or failed, because a stream stopped over a running card has Slack stamp it failed itself. The answer and every card title go out as raw markdown with the three mention openers neutralised, so nothing the model writes can ping a human or the channel: Slack folds a card's title into the message's own text, where a raw `<@U…>` is a real mention. Discord gets the same guarantee from `allowed_mentions`.
	- A Slack thread has no free-text status, so what mate is doing is the cards' to say and that it is working at all is the agent session's: `agents.sessions.setStatus` sets the thread's parent `processing` before the first token and `active` when the turn ends, which is what Slack's own loading UX reads, and teardown closes the session. Nothing moves a session on its own — `chat.stopStream` leaves it `active` and only the `processing` expiry passes unasked — so every one of those is mate saying so. That expiry is an hour, and streaming into the thread does not push it out; a turn re-asserts `processing` every half hour while it runs, because a thread that reads as idle under a working harness loses Slack's stop control with it. The harness's own cap on one turn is `MATE_TURN_MINUTES`, which can be set past the hour, so the re-assertion renews for as long as a turn runs rather than once.
	- Stop on Slack is Slack's own control, drawn on a `processing` session because the app subscribes to `agent_session_stopped`. mate has no button here: the press arrives as that event on the socket, names the channel and thread — which together are a thread's key — and the human who pressed it, and drops into the one cancel the state machine has, the same one the Discord button reaches, allowlist check and all. Slack ends the stream as it sends the event, so the frame mate had in flight is refused with `stopped_by_user` or `message_not_in_streaming_state`: both mean the turn is already over, so neither is a line in the thread or an error in the metrics, and the turn ends cancelled exactly as it does on Discord.
	- Slack's reads are form-encoded and its writes are JSON, which is not a style choice: `conversations.replies` answers `invalid_arguments` naming a field that is in the body it was sent, and `users.info` answers `user_not_found` for a user who exists, when either is given a JSON body. JSON is what a stream's chunks need, and it is the exception rather than the rule.
	- Everything inbound arrives on one Socket Mode WebSocket: the mentions mate answers and the stop Slack draws itself. mate reads `message` events and finds mentions in the text: one human sentence also arrives as an app-mention under a second event id, and reading one type alone is what makes it one answer rather than two, whatever the app is subscribed to. Its own posts come back down the same socket carrying a bot id and no subtype, so the bot id is what tells them apart, and a message from mate's own id is never a prompt whichever shape it arrives in. Every envelope is acknowledged on receipt, inside Slack's three seconds, and answered at most once by its event id.
	- The Slack half is opt-in, and nothing about it can take the Discord half down. With neither of its tokens set mate answers on Discord alone; with one of the two set it refuses to start rather than run half a surface. Both are optional environment variables, so a Secret that does not exist yet leaves Slack off instead of holding the pod in `CreateContainerConfigError`, and a workspace that cannot be reached at start is one error line rather than a restart. Slack comes up first and on its own: its socket is open and its threads are re-attached before the Discord gateway is dialled, so each surface answers while the other is down.
- ## What is true today
	- Every thread gets a real sandbox: `MATE_SANDBOXES` is `kube`, so mate mints one `Sandbox` per thread, execs `opencode acp` in its pod and streams the turn back into the thread. The other value is `stub`, an in-process reply with no cluster behind it.
	- The agent arrives holding this repo's own rules and not only its skills. `OPENCODE_CONFIG_CONTENT` names `AGENTS.md` as the harness's `instructions` and `dotfiles/skills` under its `skills.paths`, and both have to be named out loud. opencode walks up from the cwd for `.agents/` and `.claude/` whatever else is configured, so every `SKILL.md` under `.agents/skills/` arrives on its own — and the hard rules those skills are written on top of do not, because an instructions file comes with the project config this harness turns off. `dotfiles/skills/` is neither of the two directory names that walk knows, so the skills in it are invisible until something points at them. `OPENCODE_DISABLE_PROJECT_CONFIG` stays set: the checkout's own `.opencode/` npm-installs a plugin package on every start whether or not a plugin is declared there, and npm is not a name a sandbox may reach. The same config sets `permission: allow`, so nothing the agent decides to run is put to a human first, and the vault and the egress policy below are therefore the whole of the answer to what a sandbox can do.
	- git works inside a sandbox because both containers are handed a git configuration in git's own command scope. kubelet's `fsGroup` chown sets an emptyDir mount root's gid and leaves its uid at root, so `/workspace` belongs to uid 0 whoever clones into it, and git checks the worktree root as well as the git directory: the clone succeeds and every command after it dies on dubious ownership, which opencode reads as the checkout not being a repository at all and answers by dropping its snapshots without a word. `gitEnv()` in `apps/mate/src/sandboxes.ts` hands both containers `safe.directory`, `user.name` and `user.email` through `GIT_CONFIG_COUNT` and its numbered pairs — git's command scope is protected configuration, which is what makes `safe.directory` honoured there and what makes it stick with nothing written into the image or into a home directory that is itself an emptyDir. The ident is load-bearing beside it: the image's agent user carries no GECOS, so without one handed in `git commit` dies on an empty ident name.
	- A sandbox can finish the loop its checkout starts without a GitHub token ever sitting in its environment. `MATE_GITHUB_TOKEN_REF` is one `op://` reference — vault, item and field in the single string `op read` takes — and the harness container gets a git credential helper scoped to `https://github.com` that answers a password by reading it, so the token is inside one process for the length of a push rather than in the pod for the length of the thread. What reads it is a 1Password Connect token from the `mate-onepassword` Secret, and that token's own claims name exactly one vault: the one stocked for the sandbox, which is not the `homelab` vault every other credential in this namespace comes out of. The vault is the security boundary and it is the only one there is — keeping a token out of the environment is not the same as keeping it out of the agent's reach, since the agent can run `op read` itself, so whatever is put in that vault is readable by whatever the agent decides to run.
	- The identity that credential carries is sharper than its scope. The token is a fine-grained PAT on `rowbutt` that reaches this repository alone, and `rowbutt` is named twice in the Atlantis configuration: in `clusters/offsite/apps/atlantis/policies/only-me.rego`, which the plan pre-workflow hook runs against whoever commented, and under `policies.owners.users` in `clusters/offsite/apps/atlantis/helm-release.yaml`, where `apply_requirements` is empty and `ATLANTIS_AUTOMERGE` is `true`. A pull-request comment written with this credential therefore passes the plan hook, can clear a failed policy check and can start a Terraform apply, and an apply that succeeds merges the pull request to `main`.
	- `gh` needs an answer of its own, because only git consults a git credential helper. The CLI looks for a token in `GH_TOKEN`, in `GITHUB_TOKEN` or in its own `hosts.yml`, finds none of the three in a sandbox, and meets `gh pr create` with its login instructions — the loop stops one step short of the pull request the push was for. `images/mate-sandbox/gh` is what the image puts on PATH under that name, ahead of the real binary at `/usr/local/libexec/gh`: it reads the same `MATE_GITHUB_TOKEN_REF` through `op`, exports the result and execs gh, so the token is inside one process for the length of one command and in no environment on either side of it — the same trade the git helper makes, with the same limit, since the agent can read `/proc/<pid>/environ` of a gh it started as easily as it can run `op read`. An inherited `GH_TOKEN` wins over the read, which is what keeps a gh that shells out to gh from going back to the vault for a second copy. A read that fails says so and execs gh unauthenticated, because a hard exit would take `gh --version` down alongside the commands that need a credential. The image build proves it rather than trusting it — a stand-in `op` first on PATH, and `gh auth token`, which reports the credential gh would use and reaches no network to do it — and `apps/mate/test/sandboxes.test.ts` fails if the variable the wrapper reads stops being one the harness container is handed.
	- Sandboxes stay off the control-plane node, and a required `nodeAffinity` on `node-role.kubernetes.io/control-plane` not existing is the only thing keeping them off, because no node in this cluster is tainted. offsite has two nodes and [[Fleet/retrofit]] is the control-plane one, which leaves every sandbox on [[Fleet/oldschool]]. `MATE_MAX_CONCURRENT` is 2 for that reason rather than as a matter of policy, and it is a cap on threads rather than on sandboxes: with one spare warm, three of them share that node at peak. Measured, that is about 3 GiB of the 9 GiB oldschool has free. Declared, it is three 4Gi limits on a node whose limits are already 92% committed with no sandbox on it at all — 19 of its 37 other pods name no memory limit, so the limit on a sandbox is a bound on one of them running away rather than an allocation the node has set aside.
	- mate keeps one sandbox warm. `MATE_SPARES` is 1 on the Deployment, so mate holds a spare — the same object any thread gets, carrying a spare marker in place of the thread labels — and a thread takes it by swapping those labels in a single patch, which costs a shallow fetch to bring the spare's checkout up to date rather than a kata VM boot and a clone. Measured on oldschool, that is the difference between a 46.8 s mint and a relabel; what a spare does not remove is the ACP attach at 4.9 s and the harness's own 4.4 s to its first token. The replacement is minted the moment a thread takes one, so the pool is a sandbox's worth of the node held for as long as mate is up rather than only while a thread is being served. A spare carries a half-hour `shutdownTime` that mate's own sweep is the only thing renewing, so a mate that stops running hands its spares back; a thread's sandbox carries two hours, slid by every turn. mate keeps none of the spares it finds when it starts, because a spare outlives the roll that changes the sandbox image, the model or the checkout it was built from. A spare holds a whole sandbox's memory while it waits, out of the same room on the node that `MATE_MAX_CONCURRENT` spends.
	- A turn gets a whole window of its own. `MATE_TURN_MINUTES` caps one harness call at 45 minutes on the Deployment, and mate refuses to boot on a value at or past the two-hour `shutdownTime` every sandbox is minted with, because a cap past the TTL promises a turn a window no sandbox lives long enough to give. The TTL slides at both ends of a turn: the patch that stamps the turn mark pushes `shutdownTime` out again, and the turn's end slides it once more. The slide at the start is what keeps the two clocks apart — the controller deletes a sandbox the moment `shutdownTime` passes and does not care that a turn is streaming out of it, so without it a turn's real ceiling would be whatever `MATE_QUIET_MINUTES` had not already spent.
	- A thread's harness state lives on the sandbox's own filesystem, keyed by the ACP session id mate keeps in an annotation on the Sandbox. mate re-opens it with `session/load`; when that fails — a fresh sandbox after quiet, a harness that cannot replay — the new session's first prompt carries the thread's own transcript, read back from whichever surface holds it, capped at the newest 40 messages or 8000 characters. mate's own status and teardown lines are not part of it.
	- A turn in flight is stamped on the Sandbox and cleared when the turn ends, so a mate that dies under a running turn knows which threads lost an answer. On the next start it rehydrates from the Sandboxes it finds and tells each of those threads once, in plain words, before carrying on — and tells the surface too, where its working sign belongs to the thread rather than to a message and so outlived the turn that raised it. Slack's agent session is the one such sign; Discord's is a message mid-edit, which ends with the process.
	- Every state change of every thread is one info line naming the thread, the state, the sandbox and the turn count. The metrics — sandboxes live, queue depth, sandbox mints by result, turns started and ended by stop reason, teardowns by reason, time to first token, USD per turn, how long a mint and an attach each take, gateway closes by code, and Discord's identify budget — are minted on first use, because an OpenTelemetry instrument created before an SDK starts is a no-op forever. The two duration histograms carry a `source` label that separates a fresh mint from a reuse of the thread's own sandbox and from a warm spare, which is the only thing that says which wait a thread actually paid. `apps/mate/src/telemetry.ts` registers the SDK before anything can reach a meter and ships them over OTLP to the cluster's collector, which is the one destination in `monitoring` mate's egress policy allows. It also gives every histogram bucket edges of its own, because the SDK's defaults stop at 10 000 and a mint spends its time in the seconds, where a bucket spanning 5 s to 15 s reports nothing but its own edges: `histogram_quantile` interpolates inside whichever bucket a sample lands in. With `MATE_OTEL_ENDPOINT` unset — a workstation run, `bun test` — no SDK is registered and every instrument stays the no-op it is born as.
	- The instruments are named the way Prometheus holds them rather than in OpenTelemetry's dotted style, because the collector's prometheus exporter rewrites a dotted name on its way out and an alert can only be written against the name that survives. Their series reach Prometheus through the collector's `prom-metrics` scrape, so they carry the collector's namespace and mate's own name as `exported_job`.
	- `clusters/offsite/monitoring/mate-rules.yaml` is what watches them: mate down or its gateway disconnected, its metrics gone while it is up, a Discord close code that never retries, the sandbox cap held for half an hour, turns and mints failing, and both halves of the budget — turns against the daily 120 and the reported spend. Alertmanager sends them to Discord, in the same guild mate serves. `clusters/base/monitoring/grafana-dashboards/mate.json` is the same series as a dashboard. The alerts have a promtool unit test beside them, run by `mise run k8s:check-rules`.
	- A sandbox reaches three things. Its own `CiliumNetworkPolicy` selects `app.kubernetes.io/name: mate-sandbox` and allows four names on 443: `opencode.ai` and `models.opencode.ai` for the model, `github.com` for the init container's clone and for the whole of a `git push` — smart HTTP never leaves the host it cloned from — and `api.github.com`, the separate host every REST call goes to, opening a pull request among them. The GitHub names left out are deliberate: `codeload.github.com` and the two asset hosts move tarballs and release files, a file-shaped way out that a commit and a pull request never need; npm is absent beside them, the second lock on the door `OPENCODE_DISABLE_PROJECT_CONFIG` closes. Then cluster DNS through Cilium's DNS proxy; and every pod in every namespace on every port — so a job can reach kthx, Spindrift's MCP or a CNPG Postgres, and so it can also read anything else the cluster serves unauthenticated, VictoriaLogs and Prometheus included. Trading that away is one field: an `In` set of namespaces in place of `Exists`. DNS is unrestricted in the same spirit — `toFQDNs` needs the lookups to pass through the proxy, and CoreDNS forwards whatever it is asked. The LAN, the node addresses, anything on host network, the API server and the cloud metadata address are denied by omission, and kata-clh isolates the kernel rather than the network, so this policy is the whole network boundary. In-cluster destinations are named by identity rather than by address because Cilium translates a ClusterIP to its backend before the egress verdict and CIDR selectors do not match in-cluster endpoints: no CIDR appears in the file at all. No ingress rule — exec arrives through the API server.
	- The bot pod holds a ServiceAccount token, so it also holds a `CiliumNetworkPolicy`: egress to Discord and Slack by name, to cluster DNS, to the API server, and to the OTLP collector's own pod labels on one port, and nothing else. Both surfaces need a pattern beside their exact names, for the same reason: each hands back a host at connect time — Discord a region-specific resume url, Slack the `wss-` host a Socket Mode connection is opened on — that mate cannot name ahead of being told it. The collector is named by its labels rather than by its namespace, because `monitoring` also holds Prometheus, Alertmanager, VictoriaLogs and Grafana. Cilium enforces per direction, so ingress stays unenforced and the readiness probe keeps working.
	- One replica with `strategy: Recreate`, which both surfaces need for opposite reasons. Discord delivers every event to every gateway session on a token, so two overlapping mate pods would both reply. Slack splits payloads across an app's connections, so two would each receive a random half and mate would look like it was ignoring people; the connection count in Slack's `hello` frame is what says so in the log.
	- The probe is readiness only. `/healthz` answers 503 whenever the gateway is disconnected, including during the budget guard's deliberate sleeps, and a liveness probe on it would kill the process for protecting the identify budget.
	- Gateway session info sits on an emptyDir so a container restart in the same pod resumes rather than identifying again.
	- A rotated token reaches the pod without waiting for Discord to close the stale session: the ExternalSecrets refresh hourly and reloader rolls the Deployment when either Secret changes.
	- No HTTP surface: no Gateway, HTTPRoute, certificate or DNS name, and so no request signature to verify. Both the Discord gateway and Slack's Socket Mode are outbound WebSockets.
