- mate is the bot Rowbutt connects through, in two places: a human mentions Rowbutt in an allowed channel, a thread opens from that message, and the reply streams back into it. The thread is the session; one thread owns at most one sandbox, one allowlisted human drives it, and a second human in a thread shares its sandbox. mate never runs a model itself — it is a client of whatever surface it is answering on plus an Agent Client Protocol client, and the coding agent runs inside a per-thread sandbox on [kubernetes-sigs/agent-sandbox](https://github.com/kubernetes-sigs/agent-sandbox).
- ## Where it lives
	- `apps/mate/src/` is the process: one Bun program with the surfaces, the thread contract, the identify-budget guard and `/healthz`. The sandbox side lives there too — the Kubernetes client on Bun's own `fetch` and `WebSocket`, the ACP client, and the `Sandboxes` implementation that mints one Sandbox per thread. `bun test` covers both against fakes, the cluster half against an in-process apiserver.
	- `clusters/offsite/apps/mate/` is the workload on the offsite cluster: the `mate` namespace at Pod Security `restricted`, the ServiceAccount and Role that mint Sandboxes, the ExternalSecrets that carry Rowbutt's tokens and the OpenCode key from 1Password, an egress policy for the bot and a second one for the sandboxes, and one Deployment. It is raw manifests under Flux, not a chart and not a Spindrift App.
	- `images/mate-sandbox/` is the harness image a sandbox runs: debian-slim with `opencode`, git and ripgrep, uid 1337, and a keepalive PID 1 that mate execs into.
	- `.github/containers.json` names both images in `build` and this Deployment in `deploy`, so every build of `apps/mate` or `images/mate-sandbox` that lands on `main` opens a digest-bump PR through the CD App identity. Both refs in the Deployment carry a digest, which is what keeps the two rewrites off each other: the anchored rewrite matches `ghcr.io/…/mate…@sha256:` and `ghcr.io/…/mate-sandbox…@sha256:` separately, and the unanchored fallback only reaches a manifest that names an image without a digest beside it.
- ## The surfaces
	- A surface is one place mate is present: its own bot identity, its own allowlists, its own ids. The thread state machine and the renderer only ever see that port, so the caps belong to mate rather than to either place — one queue, one concurrency limit, one daily budget across both, because it is one process. A thread is keyed by its surface, and a Sandbox is named and labelled from that key, so the two estates cannot collide.
	- **Discord.** A mention in an allowed channel of the homelab guild opens a public thread. One reply message is edited in place as text arrives and sealed into a new one at the 2000-character cap, with an italic status line above the live text and a red Stop button below it, both gone when the turn ends. mate archives the thread at teardown, because it is the thread's creator.
	- **Slack.** A mention in an allowed channel of the Folly Mountain Laboratories workspace makes that message the parent of a thread, which is all a Slack thread is. The answer is streamed rather than rewritten: `chat.startStream` and its `append`/`stop` take chunks, addressed to the human who asked with `thread_ts`, `recipient_user_id` and `recipient_team_id`, all three of which a mention already settles. Every stream opens in chunk mode, because the mode is fixed at the first call and a stream opened on plain markdown refuses chunks thereafter. A `markdown_text` chunk is answer text; a `task_update` chunk is one tool call, which Slack merges by its id into a task card in the same message and mutates in place as the call runs, finishes or fails. `task_display_mode` on the first call is the choice of how those same chunks render — a card per call, or the one plan block summarising them — and mate sends `timeline` for the cards, because a turn's tool calls are discovered one at a time rather than announced up front. A card still running when the turn ends is closed with it, complete on a turn that finished and errored on one stopped or failed, because a stream stopped over a running card has Slack stamp it failed itself. The answer and every card title go out as raw markdown with the three mention openers neutralised, so nothing the model writes can ping a human or the channel: Slack folds a card's title into the message's own text, where a raw `<@U…>` is a real mention. Discord gets the same guarantee from `allowed_mentions`.
	- A Slack thread has no free-text status, so what mate is doing is the cards' to say and that it is working at all is the agent session's: `agents.sessions.setStatus` sets the thread's parent `processing` before the first token and `active` when the turn ends, which is what Slack's own loading UX reads, and teardown closes the session. Nothing moves a session on its own — `chat.stopStream` leaves it `active` and only the `processing` expiry passes unasked — so every one of those is mate saying so. That expiry is an hour, and streaming into the thread does not push it out; a turn re-asserts `processing` every half hour while it runs, because a thread that reads as idle under a working harness loses Slack's stop control with it. The harness's own cap on one turn is `MATE_TURN_MINUTES`, which can be set past the hour, so the re-assertion renews for as long as a turn runs rather than once.
	- Stop on Slack is Slack's own control, drawn on a `processing` session because the app subscribes to `agent_session_stopped`. mate has no button here: the press arrives as that event on the socket, names the channel and thread — which together are a thread's key — and the human who pressed it, and drops into the one cancel the state machine has, the same one the Discord button reaches, allowlist check and all. Slack ends the stream as it sends the event, so the frame mate had in flight is refused with `stopped_by_user` or `message_not_in_streaming_state`: both mean the turn is already over, so neither is a line in the thread or an error in the metrics, and the turn ends cancelled exactly as it does on Discord.
	- Slack's reads are form-encoded and its writes are JSON, which is not a style choice: `conversations.replies` answers `invalid_arguments` naming a field that is in the body it was sent, and `users.info` answers `user_not_found` for a user who exists, when either is given a JSON body. JSON is what a stream's chunks need, and it is the exception rather than the rule.
	- Everything inbound arrives on one Socket Mode WebSocket: the mentions mate answers and the stop Slack draws itself. mate reads `message` events and finds mentions in the text: one human sentence also arrives as an app-mention under a second event id, and reading one type alone is what makes it one answer rather than two, whatever the app is subscribed to. Its own posts come back down the same socket carrying a bot id and no subtype, so the bot id is what tells them apart, and a message from mate's own id is never a prompt whichever shape it arrives in. Every envelope is acknowledged on receipt, inside Slack's three seconds, and answered at most once by its event id.
	- The Slack half is opt-in, and nothing about it can take the Discord half down. With neither of its tokens set mate answers on Discord alone; with one of the two set it refuses to start rather than run half a surface. Both are optional environment variables, so a Secret that does not exist yet leaves Slack off instead of holding the pod in `CreateContainerConfigError`, and a workspace that cannot be reached at start is one error line rather than a restart. Slack comes up first and on its own: its socket is open and its threads are re-attached before the Discord gateway is dialled, so each surface answers while the other is down.
- ## What is true today
	- Every thread gets a real sandbox: `MATE_SANDBOXES` is `kube`, so mate mints one `Sandbox` per thread, execs `opencode acp` in its pod and streams the turn back into the thread. The other value is `stub`, an in-process reply with no cluster behind it.
	- A thread's harness state lives on the sandbox's own filesystem, keyed by the ACP session id mate keeps in an annotation on the Sandbox. mate re-opens it with `session/load`; when that fails — a fresh sandbox after quiet, a harness that cannot replay — the new session's first prompt carries the thread's own transcript, read back from whichever surface holds it, capped at the newest 40 messages or 8000 characters. mate's own status and teardown lines are not part of it.
	- A turn in flight is stamped on the Sandbox and cleared when the turn ends, so a mate that dies under a running turn knows which threads lost an answer. On the next start it rehydrates from the Sandboxes it finds and tells each of those threads once, in plain words, before carrying on — and tells the surface too, where its working sign belongs to the thread rather than to a message and so outlived the turn that raised it. Slack's agent session is the one such sign; Discord's is a message mid-edit, which ends with the process.
	- Every state change of every thread is one info line naming the thread, the state, the sandbox and the turn count. The metrics — sandboxes live, queue depth, sandbox mints by result, turns started and ended by stop reason, teardowns by reason, time to first token, USD per turn, gateway closes by code, and Discord's identify budget — are minted on first use, because an OpenTelemetry instrument created before an SDK starts is a no-op forever. `apps/mate/src/telemetry.ts` registers the SDK before anything can reach a meter and ships them over OTLP to the cluster's collector, which is the one destination in `monitoring` mate's egress policy allows. With `MATE_OTEL_ENDPOINT` unset — a workstation run, `bun test` — no SDK is registered and every instrument stays the no-op it is born as.
	- The instruments are named the way Prometheus holds them rather than in OpenTelemetry's dotted style, because the collector's prometheus exporter rewrites a dotted name on its way out and an alert can only be written against the name that survives. Their series reach Prometheus through the collector's `prom-metrics` scrape, so they carry the collector's namespace and mate's own name as `exported_job`.
	- `clusters/offsite/monitoring/mate-rules.yaml` is what watches them: mate down or its gateway disconnected, its metrics gone while it is up, a Discord close code that never retries, the sandbox cap held for half an hour, turns and mints failing, and both halves of the budget — turns against the daily 120 and the reported spend. Alertmanager sends them to Discord, in the same guild mate serves. `clusters/base/monitoring/grafana-dashboards/mate.json` is the same series as a dashboard. The alerts have a promtool unit test beside them, run by `mise run k8s:check-rules`.
	- A sandbox reaches three things. Its own `CiliumNetworkPolicy` selects `app.kubernetes.io/name: mate-sandbox` and allows `opencode.ai` and `models.opencode.ai` for the model and `github.com` for the clone, on 443 by name; cluster DNS through Cilium's DNS proxy; and every pod in every namespace on every port — so a job can reach kthx, Spindrift's MCP or a CNPG Postgres, and so it can also read anything else the cluster serves unauthenticated, VictoriaLogs and Prometheus included. Trading that away is one field: an `In` set of namespaces in place of `Exists`. DNS is unrestricted in the same spirit — `toFQDNs` needs the lookups to pass through the proxy, and CoreDNS forwards whatever it is asked. The LAN, the node addresses, anything on host network, the API server and the cloud metadata address are denied by omission, and kata-clh isolates the kernel rather than the network, so this policy is the whole network boundary. In-cluster destinations are named by identity rather than by address because Cilium translates a ClusterIP to its backend before the egress verdict and CIDR selectors do not match in-cluster endpoints: no CIDR appears in the file at all. No ingress rule — exec arrives through the API server.
	- The bot pod holds a ServiceAccount token, so it also holds a `CiliumNetworkPolicy`: egress to Discord and Slack by name, to cluster DNS, to the API server, and to the OTLP collector's own pod labels on one port, and nothing else. Both surfaces need a pattern beside their exact names, for the same reason: each hands back a host at connect time — Discord a region-specific resume url, Slack the `wss-` host a Socket Mode connection is opened on — that mate cannot name ahead of being told it. The collector is named by its labels rather than by its namespace, because `monitoring` also holds Prometheus, Alertmanager, VictoriaLogs and Grafana. Cilium enforces per direction, so ingress stays unenforced and the readiness probe keeps working.
	- One replica with `strategy: Recreate`, which both surfaces need for opposite reasons. Discord delivers every event to every gateway session on a token, so two overlapping mate pods would both reply. Slack splits payloads across an app's connections, so two would each receive a random half and mate would look like it was ignoring people; the connection count in Slack's `hello` frame is what says so in the log.
	- The probe is readiness only. `/healthz` answers 503 whenever the gateway is disconnected, including during the budget guard's deliberate sleeps, and a liveness probe on it would kill the process for protecting the identify budget.
	- Gateway session info sits on an emptyDir so a container restart in the same pod resumes rather than identifying again.
	- A rotated token reaches the pod without waiting for Discord to close the stale session: the ExternalSecrets refresh hourly and reloader rolls the Deployment when either Secret changes.
	- No HTTP surface: no Gateway, HTTPRoute, certificate or DNS name, and so no request signature to verify. Both the Discord gateway and Slack's Socket Mode are outbound WebSockets.
